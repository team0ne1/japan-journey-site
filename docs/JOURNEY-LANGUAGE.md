# Journey Markdown：行程描述语言草案

设计日期：2026-09-12。格式版本：`1.0-draft`。状态：待实施；当前网页尚未读取此格式。

本规范只定义行程内容。版本历史、成员、草稿归属、提案、评论、审批和权限由外部系统管理，见 [工程方案](JOURNEY-ENGINEERING.md)。完整的当前行程示例见 [journey.example.md](journey.example.md)。

## 1. 表达原则

一份Markdown描述一个完整旅行，包含地点资料、若干日程单元和路线方案。每个方案选定一组有序日程单元。文件可单独复制、导入、导出；不依赖另一位成员的私人文件，也不包含登录凭证或协作信息。

代码块是结构化数据，标题仅方便阅读。采用CommonMark代码围栏，并在信息字符串中标注数据类型。例如：

````markdown
## 地点 · 须磨站前海边

```yaml journey:place
id: beach
name: 须磨站前海边
lat: 34.6412
lng: 135.1136
mapQuery: Suma Beach
duration: 建议停留90分钟，其中坐下休息至少60分钟
```
````

这是地点块示例，不是一份完整可导入文件。使用标准Markdown代码块不需要自造一套标点解析规则；结构块仍须由专用Schema校验。[CommonMark代码块规范](https://spec.commonmark.org/0.31.2/#fenced-code-blocks)

不支持JavaScript、MDX、函数、模板、变量插值、文件include、YAML锚点／别名／合并键或自定义标签。说明按纯文本处理，不把文本里的HTML当组件。行程格式能表达事实与安排，不能通过文档改变认证或执行服务器操作。

## 2. 文档组成

按顺序包含：

1. 一个 `yaml journey:trip` 块。
2. 一个或多个 `yaml journey:place` 块。
3. 一个或多个 `yaml journey:day` 块。

解析器应使用Markdown语法树读取代码块及源位置，识别 `lang=yaml`、`meta=journey:trip/place/day`。未知 `journey:*` 类型、重复trip块、围栏未闭合及非白名单结构必须明确报错，不能静默忽略。禁止远程包含。

结构块外允许标题、空行及普通行程说明，但它们不参与地图、预算或行程合并；凡需要在网站呈现的主要信息，应写入对应结构字段。生成器可重建装饰标题。示例文件不携带任何评论数据。

## 3. 编号与引用

| 实体 | 示例 | 意义 |
| --- | --- | --- |
| 旅行 | `kansai-october-2026` | 同一旅行身份 |
| 地点 | `beach` | 同一个地理位置，供不同活动引用 |
| 日程单元 | `day-06-a` | 一套完整的当天安排，不能以当前数组下标识别 |
| 活动节点 | `d6-beach` | 此次在海边休息的活动身份 |
| 时间色块 | `day-06-a-slot-11` | 一段可独立调整的时间分配 |
| 费用条目 | `day-06-a-cost-03` | 一项预算构成 |
| 跨城衔接 | `day-05-to-day-06-a` | 两个日程单元之间的交接关系 |

编号仅允许小写字母、数字和连字符，长度1–80。地点、日程分别在各自类别唯一；活动节点在完整文档中唯一；时间色块、费用、备选和衔接在各自类别全局唯一。编号不能来自数组位置的即时计算，也不能因改期、改名、跨日移动而重建。

示例沿用现有节点编号以便未来兼容；其中的 `d6` 只是历史名称片段。以后将 `d6-beach` 移到另一日时仍保留编号。重新安排另一项不同活动要新建编号；同一酒店入住、回房、次日退房等是不同节点，不能只用酒店ID表示活动身份。

普通用户通过表单新增时由系统生成随机编号；AI或人工编辑文档时也必须生成新编号并通过重复检查。编号本身不是权限凭证。

## 4. 旅程块：`journey:trip`

| 字段 | 类型 | 约束／用途 |
| --- | --- | --- |
| `version` | 字符串 | 本草案固定 `1.0-draft`；仅描述语言版本，不是审核版本 |
| `id` | ID | 旅行身份；在线导入必须与会话所在旅行匹配 |
| `name` / `title` / `description` | 字符串 | 网站名称、首页标题、简述 |
| `startDate` / `endDate` | `YYYY-MM-DD` | 实际有效日期，起始不晚于结束 |
| `timezone` | IANA时区字符串 | 当前 `Asia/Tokyo`，所有时间在此时区解释 |
| `partySize` | 正整数 | 预算人数；当前5，和登录账户数量不是同一概念 |
| `weightKg` | 正数 | 活动热量估算的参考体重，当前70kg |
| `currency` | ISO货币码 | v1限定 `JPY`；不做隐式汇率换算 |
| `updated` | 日期 | 行程资料更新日期，不是提交／审批时间 |
| `hoursChecked` | 日期 | 开放信息默认核对日期；改旅行资料不自动更新核对日期 |
| `status` | 字符串 | 如“规划草案”，属于旅行安排的确定程度 |
| `intro` / `planningNote` | 字符串 | 交通与总体安排说明 |
| `plans` | 对象 | 键为 `A`、`B`，值为有序日程ID数组；A必须存在，B可省略 |
| `planLabels` | 对象 | 与plans键对应的方案名称 |
| `planNote` | 字符串 | 方案取舍说明，不代表预订确认 |
| `budgetScope` | 字符串 | 总开支包含／排除口径 |
| `budgetNotes` | 字符串数组 | 住宿分摊、套餐餐食和估算假设 |
| `handoffs` | 衔接数组 | 两日之间的实际活动引用，见下文 |

方案例子：

```yaml
plans:
  A: [day-01, day-02, day-03, day-04, day-05, day-06-a, day-07-a]
  B: [day-01, day-02, day-03, day-04, day-05, day-06-b, day-07-b]
```

前5个日程单元是共享对象，修改会影响两个方案。这里的A/B是旅行路线选择，与“领队版／成员版”无关；副本归属不在文件内定义。显示的Day1、Day2和星期由选定方案顺序及日期生成。

v1每个方案每天一个日程单元，日期严格递增且覆盖起止范围。每个日程至少被一个方案引用；未知或重复日程引用拒绝保存为有效行程。未填写完整的中间编辑内容可在表单本地保留，但不能作为可提交版本。

### 两日衔接字段

每项包含 `id / fromDay / toDay / fromStep / toStep / note`，均必填。`fromDay`、`toDay`必须在至少一个方案里相邻；`fromStep`指向前一天最终收束节点，`toStep`指向下一日需要接上的酒店、寄存点或机场等节点。

交通方式从下一天路线中到达这些节点的分段读取，不再在衔接对象复制铁路信息。`note`解释拿取行李、整段时间预算和舒适性取舍。引用可跨越下一日多个换乘点，不能把它渲染成无中间换乘的一条已验证直达线路。

若连续两日住同一酒店，可形成地点相同的衔接，此时不画城市移动线。每组方案相邻日程都必须存在对应衔接；共享日程之间的同一衔接只定义一次。

## 5. 地点块：`journey:place`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` / `name` | ID／字符串 | 地点编号及显示名 |
| `lat` / `lng` | 数字，成对出现 | 纬度-90至90，经度-180至180 |
| `mapQuery` | 字符串 | 外部地图搜索名称，导航URL由渲染器构造 |
| `googlePlaceId` | 可选非空字符串 | 经核对的 Google 地点 ID，仅作照片匹配；不代替内部固定 ID，不接受 URL／API Key。未核实则省略 |
| `duration` | 可选字符串 | 默认建议游览时长，节点可覆盖 |
| `hotel` | 可选对象 | 住宿候选资料 |
| `hours` | 可选对象 | 此地点适用的开放及进入信息 |
| `hoursFrom` | 可选地点ID | 完全相同的开放范围可复用来源地点；不得循环 |
| `tickets` | 可选票种数组 | 成人票价、适用项目、来源与核对时间；见第10节 |

路线节点、地图聚焦、时间轴的实际地点必须有坐标和mapQuery。仅作未确定位置的备选可以没有坐标，页面明确显示“位置待定”，不能画到默认0,0。示例中的鸭川备选就是未指定具体入口的范围。

`hours` 与 `hoursFrom` 互斥。共享开放信息只适用于同一开放规则，不能将贵船本宫的开放时间借给未核实的奥宫，也不能把酒店日归浴场规则套给住客。

酒店对象字段：`name / area / url / note / status`，可选 `booking / shuttle`。`status`表示候选、待确认等预订状态；`url`官网、`booking`预约入口、`shuttle`接驳说明均仅允许HTTPS链接。此处不存客人身份、订房确认码、支付信息或可直接管理订单的私密链接。

地点照片由渲染器通过官方组件按需显示，见[照片方案](PLACE-PHOTOS.md)。文档仅存经核对的 googlePlaceId，不存图片文件、临时照片引用或 API 返回内容；当前行程示例未填入尚未验证的 ID。该字段不授予网页用户编辑行程的权限。

### 开放信息对象

| 字段 | 内容 |
| --- | --- |
| `scope` | 明确是哪一区域／设施／体验 |
| `open` | 可进入或使用时段 |
| `last` | 最晚进入、受付、开席或点单时刻，必须说明类型 |
| `close` | 闭门或使用结束时刻 |
| `note` | 季节、周休、例外、信息差异和适用范围 |
| `sources` | `[标题, HTTPS网址]` 数组 |
| `status` | 已公布、未单列、来源有差异、待确认等说明 |

这些字段当前允许自然语言，以保留“最后开席不等于最晚入门”等真实差异。解析器不能把 `last: 待确认` 推断成 `close`，不能单凭自然语言保证自动发现所有入场冲突。必要时另加经过确认的结构化约束；没有机器可读约束时提示人工复核，不声称已经核验开放可行性。

## 6. 日程块：`journey:day`

| 字段 | 类型／用途 |
| --- | --- |
| `id` | 稳定日程ID |
| `date` | `YYYY-MM-DD`，处于旅程范围内 |
| `city / title / subtitle` | 城市、标题和当日节奏说明 |
| `distanceKm` | `[最小值, 最大值]` 数字数组，非负；包含景区内与上下坡 |
| `activityKcal` | 同样的非负区间，活动额外消耗参考，不含基础代谢 |
| `intensity` | 如轻松、适中、有坡度、较充实 |
| `hotel` | 地点ID或null；非null时该地点须有hotel对象 |
| `focus` | 地点ID数组，今日地图的游览聚焦范围 |
| `luggage / next / rest` | 行李安排、次日衔接和恢复体力说明 |
| `notes` | 尚待确认事项的字符串数组 |
| `links` | `[标题, HTTPS网址]` 数组 |
| `optional` | 备选数组，每项 `id / place / note` |
| `overview` | 本日要在全程地图显示的节点ID数组，保持当天路线次序 |
| `budget` | 预算对象 |
| `dining` | 用餐记录数组；当前无预订为空数组。只有confirmed的餐厅可归入餐饮费用，见第10节 |
| `schedule` | 连续时间分配对象 |
| `stops` | 有序活动节点数组 |
| `constraints` | 可选，已确认的结构化时间约束，见第9节 |

`next`供用户阅读，`handoffs`提供可追踪结构引用。两者的说明如果互相矛盾，需在审核中提醒；机器不能保证理解每段自然语言。今日住宿应与最后收束及翌日起点一致；若实际夜间移动或特殊情况需要例外，在行李和衔接说明中明示。

每天的金额合计与时间色块总时长由字段计算，不存重复的手写总数。步行距离和热量目前是人工估算，不能由地图直线距离算出真实徒步距离，也不能在路线变化后静默沿用并标记为“重新计算”。路线、爬坡、停留或参考体重变化时，审核界面应提示重新评估。

## 7. 活动节点与地图

节点字段：

```yaml
id: d6-beach
place: beach
time: 13:30–15:00
mode: walk
connection: 车站至海边短距离步行
note: 站前海边短走、喝咖啡、坐下看海，至少休息60分钟。
```

`id / place / time / mode / connection / note`必填；`duration`可选，省略时采用地点默认时长，空字符串表示此节点不显示时长推荐。`fees`为可选票价展示引用，节点与optional项目都可使用，见第10节。

- `time`是概括性展示文字，如“上午”“按末班倒排”，不充当精确计算输入。
- `mode`与`connection`解释从**前一个节点到当前节点**的交通，首节点可空连接说明。v1允许 `walk / rail / bus / shuttle`。
- 路线来自节点顺序，不把“先去哪个地方”再复制成另一张路线表。
- 相同place可出现多次，节点ID必须不同，例如先寄存再回房。
- 坐标连线仅示意路线顺序，不是已验证道路轨迹。步行和公共交通导航由对应分段生成。

初期保留 `time` 的原因是现有行程仍包含未定航班及不确定班次。精确横轴使用 `schedule`，不要尝试把“下午”自动变成14:00。修改时，若节点时间说明与色块安排明显不一致，应在预览提示复核；以后可让表单从色块生成展示标签，减少重复输入。

## 8. 时间轴

`schedule`字段：`start / note / slots`必填，`relative`可选，默认为false。

### 实际钟表排程

```yaml
start: "13:20"
note: 海边与往返交通为暂定预留。
slots:
  - id: suma-to-beach
    end: "13:30"
    type: travel
    label: 步行到海边
    place: beach
    step: d6-beach
  - id: beach-rest
    end: "14:30"
    type: free
    label: 海边坐下休息
    place: beach
    step: d6-beach
  - id: beach-stroll
    end: "15:00"
    type: visit
    label: 海边短走
    place: beach
    step: d6-beach
```

这是一段局部示例。前一个色块结束即下一块开始；只填写总起点和每项终点，自动派生每项起点、分钟数和宽度，不允许重复填duration造成冲突。时间使用有引号的 `HH:mm`；v1允许00:00–24:00，其中24:00仅可用作最后结束。跨午夜更长的实际安排需拆到下一日，或后续升级格式，不能把结束00:30解释为当日倒退。

色块字段：`id / end / type / label`必填，`place / step / note`可选。类型为 `travel / visit / meal / hotel / free`；颜色、字体、圆角和交互写在网页渲染器中，行程文件不控制CSS。

`step`引用本日节点；若同时提供place，两者必须一致。同一节点可以有多个色块（比如海边休息和短走），多个换乘节点也可以由一个综合通行色块概括。`step`不是评论字段，不使个人版本获得评论资格。

没有确定餐厅的用餐／自由活动允许没有place和step。已有place但没有step时，只渲染时间安排，不强行按地名猜一次活动。路线顺序和色块关联顺序应校验；往返同一地点必须指向正确的一次活动。

### 航班未定时的相对排程

`relative: true`时，start和end必须都是整数分钟，不使用钟表字符串。0表示离开酒店，负数表示离店前。

例如start=-90，早餐end=-45，退房end=0，接驳end=15。整日相对色块严格递增，最终结束是预算边界，不是已确认起飞时间。日程说明必须明确离店基准、机场提前量和待核班次。

v1不允许同一时间轴混用实际时间和相对分钟；已知航班后需要整体转换并复核。留白也应显式写free色块，让休息时间在同一行可见。酒店色块仅代表画出的时间段，不据此自动计算整晚睡眠时长。

## 9. 已确认的结构化时间约束

当前完整示例保留旧网站开放文字，不会凭此生成机器已确认的截止规则。未来可在日程的 `constraints` 显式填写以下统一结构：

```yaml
constraints:
  - id: wakakusa-exit-limit
    kind: end-not-after
    slot: day-05-slot-16
    time: "17:00"
    source: https://www.pref.nara.lg.jp/site/park/2585.html
    checked: "2026-09-11"
    note: 仅适用于已确认的收费草坡退出要求。
```

这是格式说明，不代表示例中的某个slot已被自动绑定为这一规则，实际实施必须由规划人选中正确的下山色块。

`kind`暂限 `start-not-before / end-not-after / start-at`；time为本地 `HH:mm`；slot必须是本日时间轴存在的ID；必须给source、checked和note。仅适用于实际钟表排程，相对时轴不能和绝对截止时间直接比较。

违反已确认约束应阻止作为可发布版本；未确认末班、日落天气、排队及自然语言例外只产生人工复核提示。约束本身被修改或删除也属于待审核的行程变化，不能通过删除约束来假装旧安排已被证明可行。

## 10. 费用

`budget`包含 `summary / items / notes`，可选 `sources`。

费用条目分为三类，不能同时填写多类金额：

- 手工预留项含 `id / name / kind / currency / min / max / note / confirmed`，`source`可选或null；可加 `category`（transport/admission/experience/other）以及 `coveredTickets`，后者表示票价已包含在该预留中。
- 票价引用项含 `id / name / kind / category / ticketOptions / quantity / step / note`，金额、币种、来源与核价状态从ticketOptions指向的地点票种派生，不重复填写min、max、currency、source或confirmed。
- 已预订餐饮引用项含 `id / name / kind / category / diningRef / note`，kind为daily、category为dining，金额与来源从同日dining记录派生，不重复手填价格。

```yaml
id: day-06-a-cost-01
name: 交通
kind: daily
category: transport
currency: JPY
min: 3000
max: 4500
note: 奈良至神户、神户市内交通与前往有马的规划预留。
confirmed: false
source: null
```

- v1为每位成人、同一币种JPY的规划预算，数值为非负整数且min≤max。
- `kind`为 `daily / lodging`，用来计算含住宿及不含住宿总额，不能通过中文名称识别住宿。
- 每条币种必须与trip.currency一致。混入CNY要拒绝，不能直接相加；将来支持多币种时需另定义汇率日期与来源。
- `confirmed: true`仅表示有官网票价基准和source，不表示已购票、已经预约或该日一定有库存。
- 当前统计合计为符合纳入规则的条目区间分别求和；显示“不含未预订餐饮”，不能称为完整旅行开支。同行合计按实际预订人数计算；全团同餐同标准时才可直接乘partySize。
- 套餐餐饮是否已含、税费、寄存、备选项目和未含消费应写在条目或预算说明中。
- optional里的项目不默认进入主线预算；采纳进主线时要增加相应费用，不能只移动地点卡。

### 餐饮只统计已预订餐厅（2026-09-12补充）

日程里的用餐时间与费用是否纳入是两回事：未预订午饭仍可保留meal色块，但不生成餐饮预留项。选好餐厅、正在询位或看到Tabelog“可预约”均不等于已经订位成功；只有确认预订后才计入。

日程的 `dining` 每项包含：`id / place / meal / status / participants / note`，可选 `step / time / price`。id为固定用餐事件编号；place必须是已有餐厅地点；meal为breakfast/lunch/dinner/snack；status为candidate/pending/confirmed/cancelled；participants为正整数且不超过partySize。step如存在须对应同日同地点节点，time为实际预订时刻或明确待确认说明。

`price`保存 `currency / min / max / basis / source / checked / note`，所有金额为成人每人JPY，min≤max；缺失价格用null区间或省略price，不能填0。basis为booked-course（已订套餐确定价）、tabelog-budget（Tabelog餐段预算）或tabelog-review-budget（平台消费预算统计参考）。预订状态是行程事实，不是成员提案的审批状态；不保存订位人私人资料、确认码、邮箱或订单管理链接。

只有status=confirmed的用餐记录可以被预算项的diningRef引用，且只计一次。candidate、pending、cancelled不得出现在计入餐饮的费用项中。没有任何confirmed记录时显示“暂无已预订餐厅，餐饮未纳入”，不能把统计为0描述成免费吃饭；有已预订但价格未核实的记录则显示“已预订餐厅待计价”，合计保留不完整标识。

价格核对顺序：已有已订套餐确定价优先；否则查同一分店、对应午餐或晚餐的Tabelog预算区间。平台消费统计只能作为明确标识的参考，不与店家预算混合；保留税费、服务费、席费和饮品是否已含的说明。缺少对应餐段的数据时继续待核实，不用晚餐价格套午餐、不取区间中点冒充实价。每个来源附具体店铺链接和查询日期。

餐饮预算按price区间×participants生成该餐全团金额；每日每人指标可按全团合计÷partySize展示“全团分摊参考”，不得把只预订3人的餐直接当5人全员消费。前端的统一预算模型应明确区分每位成人基价、实际参与人数和全团分摊，以免叠乘人数。

酒店一泊两食或含早套餐中的餐费不另列独立餐饮；继续包含在住宿整体预算中。酒店未预订时只是套餐假设，不表示餐厅或客房已订／已付款。未来换房型不自动补一笔泛化晚饭费用，新增独立餐饮仍需确认餐厅预订。茶道体验继续归experience，不能误当未订餐厅费用删掉。

网页餐厅节点展示“已预订＋午餐／晚餐＋人均JPY区间＋Tabelog参考／已订套餐价”，日费用明细引用同一记录。未预订餐厅显示“未计入”，不以粗略日均餐费补齐。该规则不影响门票、交通与住宿各自原有的预算口径。

### 成人票价记录与计费引用（2026-09-12补充）

每个地点的 `tickets` 数组保存适用票种。必填字段：`id / name / category / audience / currency / amount / priceStatus / checked / source / note`。可选 `booking / sources / eventDate / channel`；sources采用已有的标题与URL二元数组。每个ticket.id全局唯一，不能因票价变化而改编号；替换另一票种则创建新编号。

- audience固定adult，quantity是每位成人所需的票数，当前均为1；同行人数由partySize在展示总额时相乘一次。
- category为admission（入场）、experience（体验）、transport（乘车）。
- amount为非负整数，currency为JPY；0只能用于明确免费。未知金额填null，priceStatus为unknown，不能自动当0。
- priceStatus为verified（运营方／政府活动官方直接资料）、reference（旅游机构等参考）、unknown（未核实）。checked是本次查询日期，不表示价格必然有效至旅行日。
- source为HTTPS来源页。未知价格也要记录查阅过的页面，并在note说明为何未确定；eventDate可用于限定花火等日期专属票，不能套用其他年份价格。
- 不采集儿童、学生、团体或特殊优惠充当普通成人票；不以“起价”冒充所选日期确定价格。特殊费用、税与预订条件写入note。

例子（普通成人票）：

```yaml
tickets:
  - id: otagi-adult
    name: 爱宕念佛寺普通入场
    category: admission
    audience: adult
    currency: JPY
    amount: 1000
    priceStatus: verified
    checked: "2026-09-12"
    source: https://www.otagiji.com/visit-en
    note: 普通成人单人入场。
```

节点或备选项的 `fees` 为一组引用，每组包含 `ticketOptions / accounting`，按需要包含budgetItem。ticketOptions只能是**互斥选择**的票种，如同一场花火的线下票和Pia票；不能把需要同时支付的茶体验和花火放在同一组。两项同时支付应建立两条预算记录。

| accounting | 含义与校验 |
| --- | --- |
| budget | 此主线票计入当天。budgetItem指向同日票价引用预算项，双方ticketOptions必须一致，step必须匹配活动节点 |
| included | 已含在一个整体交通／住宿预留中；budgetItem指向同日手工预留项，且其coveredTickets必须覆盖相关票种，不重复加价 |
| optional | 当前未选的备选或额外范围，不指向计入总额的预算项；显示“未计入主线”，采纳时必须新增或替换预算项 |
| free | 仅用于所有引用票种都明确为JPY 0；显示免费，不另生成正金额费用 |

票价引用预算条目的示例：

```yaml
id: day-02-cost-02
name: 门票 · 爱宕念佛寺
kind: daily
category: admission
ticketOptions: [otagi-adult]
quantity: 1
step: d2-otagi
note: 按一位成人计费，票价与景点卡片引用同一记录。
```

票价只有一种时产生确定金额；渠道未选但所有互斥选项价格均已知时，区间为最小价至最大价，乘quantity。含未知价格的组保留“未计价项目”计数，总额显示“已知部分小计＋待确认”，不能显示成完整确定总额。参考价可以参与估算，但总额／条目必须保留参考标识。

只有预算条目是加总入口。卡片、地图弹窗、时间轴均只展示引用，不额外创建收费；同一行程方案中的同一购票事件不能被重复列入budget项。需要第二次独立付费必须有第二个活动节点和预算项，不根据place.id一概去重。共享A/B的日期只按当前方案算一次。

主线节点需要支付的每组票必须对应一个预算项，不能遗漏。备选只展示增量；改为主线时检查关联时长、交通和费用后才允许发布。特别参拜不能因路过春日大社参道就计入，东大寺大佛殿票也不能因经过南大门被计费。若换成另一种茶体验，应替换原票种，而非同时相加。

网页显示位置固定为**建议游览时长下方**，至少包括“成人门票／体验费／车票：JPY金额／人”、适用范围、核价状态与日期、计费状态、官网或预约链接。没有duration的节点仍应在地点名称下展示票价。示例里新增fees/tickets只描述旅行费用，绝不包含评论或成员信息。

核价清单与每日小计见 [成人票价核对](TICKET-PRICES.md)。这是数据与展示规范，目前尚未实现解析器／网页接入。

## 11. 序列化、校验与错误报告

后续实现必须分层校验：

| 层次 | 必须检查 |
| --- | --- |
| Markdown结构 | 一个trip、合法块类型、正确围栏和来源位置 |
| YAML值 | 重复键、类型、别名、自定义标签、非法键、深度／数量限制 |
| Schema | 必填、未知字段、数值范围、时间与日期格式、枚举 |
| 引用 | 地点、日程、节点、色块、费用、衔接ID唯一且引用存在；hoursFrom无环 |
| 方案 | 日期覆盖与顺序、共享对象影响、相邻日的完整handoff |
| 时间 | 每个色块正时长、实际／相对类型统一、已确认约束、关联节点顺序 |
| 费用 | 币种一致、区间合法、confirmed来源、票种与预算双向引用、未知价格不当0、备选排除、餐饮仅confirmed且匹配餐段与人数、套餐及交通不重复 |
| 行程完整性 | 酒店及前后两日衔接、备选依赖、改动后的体力与交通复核提示 |

JSON Schema适合类型与结构；跨日衔接、来源可信程度或某个开放时间是否真适用于收费草坡，需要业务校验和规划人判断，不能由Schema代替。

错误应含文件行列、块类型、实体ID和中文原因。例如“day-06-a：色块 beach-rest 的结束时间早于上一段”“day-05：hotel 引用不存在的地点”。解析错误不能吞掉并显示一份残缺行程。

草稿编辑过程中允许显示错误并保留作者的未完成输入；只有成功解析与校验的版本才能提交审核或发布。服务端必须重复检查，不能信任浏览器的验证结果。

规范化用于比较时：对象键顺序不影响语义，有序行程／时轴的数组顺序有意义，金额区间不排序，缺失和null不混淆。每次序列化后重新解析应得到等价模型；散文标题、缩进和排版不影响合并。

## 12. 修改指南

| 想做的调整 | 需要一起检查 |
| --- | --- |
| 海边多休息30分钟 | 色块结束与后续分配、离开海边交通、蓝调目标及晚到酒店时间 |
| 更换温泉酒店 | 地点与hotel资料、当日hotel、终点节点、接驳、费用、次日出发与handoff |
| 将景点移到另一天 | 保留stop.id，调整两个stops列表、两日时轴关联、交通、费用、focus及overview |
| 新增餐厅 | 新地点／节点ID、坐标、官网、预约与截止、用餐色块、交通及费用 |
| 去掉东大寺备选 | 删除optional项；未被引用的地点资料可保留，不影响路线 |
| 调整前5天共享日程 | 页面应提示A/B都受影响；若只改一个方案，需创建新日程单元和相应活动身份，显式分开引用 |
| 从4人变5人 | 修改partySize并复核实际房型、餐饮与交通，而非只依赖线性乘法 |

如果同一活动在两个路线方案中共享但只是日期相同，仍需判断它是否是同一项安排。v1对整日共享最明确；将共享日拆成某方案独有版本时，新副本中的活动应新建身份，外部系统可记录来源关系。评论仍仅属于领队正式节点，不能自动复制到新身份。

## 13. 格式范围与演进

v1覆盖当前旅行的完整信息并预留成员副本可比较的实体身份。暂不表达多人实时分流小队、复杂交通时刻查询、自动天气推演、订单支付、个人健康模型或实时共同编辑协议。

后续可通过新的格式版本增加结构化海拔、实际步行轨迹、预约状态、时间窗和多币种等字段。升级必须有显式迁移器、旧文档兼容测试和可回退的原文；旧解析器遇到不支持的新版本要报错，不能忽略字段后发布。

无论版本如何演进，**评论、评论作者、登录身份、提案状态、审批结果及版本关系始终属于外部协作层，不进入行程描述语言。**
